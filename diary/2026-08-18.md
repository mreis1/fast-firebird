# 2026-08-18 — Session 46: connection-wide `defaultTransaction`

## Goal
Make transaction defaults configurable per connection so high-concurrency
deployments stop repeating options at every call site (user directive after
reviewing our hardcoded implicit defaults).

## Findings
- Audit confirmed every implicit transaction (`query/run/execute/executeBatch/
  queryStream/prepare`, plus `PreparedStatement`) hardcoded a bare
  `startTransaction()` → snapshot / read-write / wait-forever, with no
  connection- or pool-level override. Bad under concurrency: snapshot RW pins
  OAT/GC, snapshot write conflicts are immediate hard errors, unbounded wait
  exhausts pools silently.
- Verified the node-firebird2-ext defaults against source (Marcio believed
  "snapshot + rec_version + read mode"): actually
  `ISOLATION_READ_COMMITED_READ_ONLY = [version3, read, wait, read_committed,
  rec_version]` + the ext's `Isolation` class forcing `lockTimeout ??= 5` and
  `upgradable: true`. So the battle-tested production pattern is: read committed +
  rec_version + read-only + 5s lock timeout + RO→RW auto-upgrade. fast-firebird
  expresses it exactly:
  `defaultTransaction: { isolation: 'readCommitted', readOnly: true, wait: 5, autoUpgradeReadOnly: true }`.
- Firebird error-shape detail (caught by the new integration test): a blocked
  UPDATE against an *uncommitted* competing record version under read
  committed + rec_version raises `deadlock / update conflicts with concurrent
  update` — for nowait immediately, and for `wait: n` after the timeout — not
  the relation-level "lock conflict on no wait transaction" / "lock time-out on
  wait transaction" texts. Tests assert timing + a message alternation.

## Changes
- `protocol/transaction.ts`: `mergeTransactionOptions(defaults, overrides)`
  (defined-field-wins merge, no mutation).
- `api/options.ts`: `defaultTransaction?: TransactionOptions` on
  `FirebirdConnectionOptions`, resolved to `{}`.
- `api/attachment.ts`: `startTransaction` merges defaults under per-call
  options (so `restart()` and auto-upgrade inherit the merged strategy);
  `run()` now routes through `tx.run` (one-shot writes gain RO→RW
  auto-upgrade + replay); `executeBatch` forces `readOnly: false`.
- Pool/drizzle/executeScript inherit for free (they build on connect options
  and `startTransaction`/`tx.run`).
- Built-in defaults left unchanged (snapshot/RW/wait) — flipping them is a
  breaking-change decision, parked; `defaultTransaction` is the escape hatch.

## Tests
- `test/unit/transaction-options.test.ts` (12): TPB byte layouts incl. the
  nf2 pattern + lock_timeout clumplet; merge semantics (override wins,
  explicit undefined doesn't clobber, no mutation).
- `test/integration/default-transaction.test.ts` (32, FB3/4/5/6): default
  reaches explicit + implicit transactions; per-call override wins; nowait
  fails fast (<500ms); `wait: 1` waits ~1s then errors; read-only default
  refuses one-shot writes; the nf2 pattern upgrades + replays them;
  executeBatch ignores readOnly; `db.transaction` path covered.
- Full suites green: 1202 core + 90 drizzle.

## Addendum: verified downstream usage contract
Read the live consumers of the nf2 ext (connection facade, pool factory,
manager commit/rollback helpers). Key facts recorded in
plans/nf2-ext-integration.md §"Verified downstream usage contract":
connection-as-transaction-context with lazy `ensureTx`, ambient
`fn(args, {tx?})` composition, never-throwing `commitP/rollbackP`
(`{err, didCommit}`), default `Isolation({mode:'read'})` (= the readCommitted/
readOnly/wait 5/upgradable pattern), context activation cleared on new tx,
`Qres.stringify`, generic-pool with destroy=detach. The shipped
`defaultTransaction` + `Attachment.run` upgrade-replay cover the semantics the
app depends on; the ext facade supplies the lazy-tx + never-throw wrappers.
